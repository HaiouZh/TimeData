# 0026 项目与标签共用一组 tint token，类型区分靠形状不靠颜色

## 状态

已采纳（2026-07-30）

## 背景

待办页有两处「用户内容身份色」：项目名 chip（`ProjectNameChip`）的圆点写死 `bg-ok`（#34d399，所有项目同一个绿）；标签 chip（`TaskRow`）的圆点走 `tagColor()` 的 12 色 hash 色板。

要让项目「各有其色」，直接给项目圆点上色会当场撞上一个既存事实：两者用的是**同一个** `META_CHIP_CLASS` 灰胶囊 + **同一个** `h-1.5 w-1.5 rounded-full` 圆点，且在同一行 meta 区并排渲染。项目点之所以能被认出来，唯一依据是「它是全场唯一的绿」——一上色这个依据即消失，只剩标签的 `#` 前缀可读。

同时 `tagColor()` 那套自身有三处不成立：

1. **色板明度与用法错配。** `TAG_PALETTE` 12 色明度 25–30%，是按 `TagFilterPanel` 选中态「填充胶囊背景 + `--color-page` 深色字」调的。`TaskRow` 拿同一组色画 6px 圆点、铺在 `#1b2336` 的胶囊底上，对比度不足以看见——那个圆点不传递任何信息。
2. **填充态本身也不可读。** `TagFilterPanel` 选中态 `backgroundColor: #2F4858` 配 `color: var(--color-page)`（#0e1320），对比度约 2.3:1，低于 4.5:1 门槛。两种用法都不成立，这组色没有一处是对的。
3. **名义 12 色，可辨 4–5 档。** `#3D5A80` / `#445A7A` / `#54667A` / `#48506B` / `#4C5C68` 是肉眼分不出的蓝灰。`turnTags.test.ts` 只钉「不塌成单色」，钉不住「人能分辨」。

## 决策

**一、一组共用 token `--color-tint-1..12`，项目与标签同源取色。** 两者都是「用户内容的身份色」，是同一件事；分两套会得到 22 个各自调和的 token，且随时间漂成两种调性。

明度定在 60–65%——这是同时满足三个约束的唯一区间：6px 圆点在 `#1b2336` 上可见、`#` 小字形可读、填充态配 `--color-page` 深字达 8:1。**提亮这一动作同时修好背景里那三处**，不是顺带优化，而是同一个根因：这组色从一开始就调在了错误的明度档。

色相避开 `--color-accent`(#4f9bf5)、`--color-ok`(#34d399)、`--color-warn`(#fbbf24) 三个已占用值。小圆点撞上唯一动作色会被当成可点元素，撞上状态色会被读成告警。

十二支的具体色值不在文档里拍板：色板挂进 `/dev/styleguide` 预览页，在真实暗底与真实尺寸（6px 圆点、caption 档 `#`）上人工验收后定稿。理由与全站视觉一致性同一条——不做像素快照，靠 styleguide 人工验收。

**二、类型区分交给形状，不交给颜色。** 圆点 = 项目，`#` = 标签。标签那个不可见的 6px 圆点删除，改为给 `#` 字符本身着色：`#` 是既有的、不需学习的类型标记，且作为字形其面积远大于 6px 圆点，同一个色终于读得出。颜色由此只承担一件事——同类型内区分个体。

圆点因此成为项目的专属形状，出现在组外行的项目名 chip 与项目区组卡片标题行两处（同色，构成「点↔点」的同一项目认同）。组卡片不另加左侧色条：同一张卡片上两个颜色信号是同一件事的两种说法，与项目区既有的「行内绿竖条与项目名 chip 排他」是同一条裁剪规则。

**三、取色是 hash 派生、不存储。** 共享内核 `lib/contentTint.ts` 的 `contentTint(seed)` = FNV-1a 取模色板。项目种子取 `goalId` 而非标题（改名不变色，色是身份不是标签），标签种子取标签名（标签无 id）。

返回 `var(--color-tint-N)` 字符串而非 Tailwind 类名：`bare-raw-color` 规则只拦裸 hex/rgb/hsl/oklch 字面量，`var()` 合规；且 `TaskRow` 标签点与 `TagFilterPanel` 三态本就是 inline style，沿用即零形态变更。走 utilities 则须为 `bg-` / `text-` / `border-` 各列 12 个类名字面量——Tailwind 4 扫不到动态拼接的类名，36 个字面量换不到任何东西。

**四、12 个裸 hex 退出 allowlist。** `TAG_PALETTE` 连同它占的 12 项 `user-content-color` 例外一并删除，`design-language-allowlist.json` 从 54 项降到 42 项。新代码零裸色、零新增例外。

## 取舍

**项目与标签会撞色，接受。** 共用 12 色、一行最多显示 3 个标签（`TaskRow` 的 `slice(0, 3)`），任一标签与项目同色的概率是 8.3% / 16% / 23%（1 / 2 / 3 个标签）——约每四条多标签任务遇上一次。这不产生歧义：类型判定已由形状闭环，撞色只留下「它们碰巧同色」这一闪念，不导致误读归属、也不导致误操作。

否决了「给标签 `#` 降一档饱和」这种第二重区分：`#` 是 caption 档小字形，提亮色板的全部目的就是让它可读，再压一档等于把刚修好的收益抚平一半——拿一个「真读不清」去换一个「弱杂念」。

**项目色不可手改，且超过 12 个项目必然撞色。** 这是 hash 派生这条路的定义。做集合内避撞就意味着颜色依赖当前项目集合，删一个项目会让其后所有项目换色；加 `color` 字段则命中 schema 停手边界（`shared` zod + SQLite 列 + 同步域 + Dexie + cli + 夹具全对齐），代价是本方案的数倍，而收益只是「能手动调色」。

**存量标签颜色全部改变。** 色板换了，不可逆也不该逆——旧色本就调在错误的明度档，其中 5 支还互相分不出。

**`--color-data-*` 与 `--color-tint-*` 并存，是两层不同的东西，不合并。** 前者服务图表数据序列（固定 6 色，不外溢 UI chrome），要求跨图表稳定可比；后者服务用户内容身份，要求个体可分辨。两个约束不同，共用会让其中一个失效。

## 备选与否决

- **形状分工（项目圆点、标签方块）**：同样能闭环类型区分，但要新造一种标记形状，而 `#` 是已经在那儿、用户不用学的类型标记。
- **一行只允许一处彩色（标签点改灰或撤掉不着色）**：最安静，但标签在任务行失去颜色身份，而筛选面板里仍有色，同一个标签两处不一致。
- **色域分家（项目暖调、标签冷调）**：两边色板各砍一半，项目只剩 5 支、撞色率翻倍；且「暖/冷」是靠学习才读出的约定，不是一眼分辨。
- **项目与标签各一套色板**：见决策一——22 个 token 两处调和，必然漂成两种调性，而「避开对方全部色相」实际做不到。
- **按创建顺序轮转取色**：前 12 个项目保证不撞色且无需存字段，但删掉一个早期项目会让其后所有项目集体换色。
- **Goal 加 `color` 字段、创建时随机**：可手改色，但命中 schema 停手边界，见取舍。
