# 0025 陌生来源提醒按「运营商(ASN)+城市」收敛，不再按精确 IP

## 状态

已采纳（2026-07-30）

## 背景

`known_ips` 表以 `(token_tier, ip)` 为主键，按**完整 IP** 判定「首见」。这在本项目的实际使用条件下不成立：

- 用户主力网络是手机流量与家宽动态 IP。运营商 CGNAT 池与 PPPoE 重拨会在「用户完全没换网络」的情况下持续更换公网地址，典型表现是前三段稳定、末段变化。
- 用户**经常开 VPN**。VPN 出口本身就是机房 IP，且同一节点会在不同连接里给出不同地址。

结果是每换一个地址就多一条告警，用户永远确认不完；而告警内容只有一串数字，没有任何可供判断「这是不是我」的信息。等于同时具备高噪音与低信息量——这类提醒最终会被整体忽略，反而不如没有。

## 决策

**一、收敛键从精确 IP 改为「ASN + 城市」，三档降级。**

| 条件 | scopeKey |
|---|---|
| 有 ASN 且查到城市 | `asn:<asn>\|geo:<cityGeonameId>` |
| 有 ASN、无城市 | `asn:<asn>` |
| 无 ASN（库缺失 / 查不到） | `net:<网段前缀>` |

城市那一档的键用 GeoLite2 的城市数字 id（`geoname_id`）而非本地化城市名。地名不是稳定标识：它随 mmdb 构建变化，且实现是 `zh-CN` 缺失时回落 `en`，同一座城市换一版库就可能换一个字符串，用名字做键会让换库后已确认的范围全部重报。另一头是碰撞：同一 ASN 下同名不同国的城市（London 英国 / 加拿大、San Jose 美国 / 哥斯达黎加）会被并成一个键，等于漏报。数字 id 两个问题都免。

城市缺失时必须退回只用 ASN，不得拼入空值——否则「未知城市」与真实城市会成为两个不同的键，噪音换一种形式回来。

`net:` 档的前缀有四种形态：合法 IPv4 取 /24；合法 IPv6 取展开归一后的 /64；真正的 IPv4-mapped / IPv4-compatible 形式按内嵌 IPv4 的 /24；**不是合法 IP 的字符串按整串当前缀**。最后一条不是理论分支——IP 取自 `X-Real-IP` / `X-Forwarded-For`，是外部可控字符串。前置闸统一用 `node:net` 的 `isIP`（与 `geoip.ts` 的 `maxmind.validate` 同一把），宁可让一个来源多报一次，也不接受把不同来源静默并成一个键。

**二、`known_ips` 表直接删除，换 `known_ip_scopes`（主键 `(token_tier, scope_key)`）。** SQLite 无法改主键；存量记录不含 ASN/城市、对新逻辑零贡献，用户已批准清空重开。

`DROP TABLE IF EXISTS known_ips` 落在 `schema.ts` 的建表段里，**每次进程启动都无条件执行**，不是一次性迁移脚本。留着只为覆盖「回滚到旧版本重建了 `known_ips`、再滚回新版本」这一种情形。**退出条件**：生产盒确认已跑过新版本后即可删除该语句；在删除之前，不得新建任何名为 `known_ips` 的表——它会在下次重启时被静默清空。

**三、归属地用 GeoLite2 离线库（City + ASN），服务端查询。** 地名取 `names["zh-CN"] ?? names.en ?? null`，缺中文名的地区落英文名。库文件由用户放进挂载目录，不进镜像。

`lookupGeo` 必须同步（`requestAudit` 在 finally 里同步调用），而 maxmind 的 `openSync` 是 `() => never`、`open` 是异步，因此走 `Reader(Buffer)` 同步构造器：`readFileSync` 把整库读进内存常驻（City ≈ 60 MB + ASN ≈ 9 MB，约 70 MB RSS），不是 mmap 按需读盘。同步构造这条路拿不到 `maxmind.open()` 自带的 LRU，所以显式给 Reader 传解码缓存，否则日志页单页 500 行就是 1000 次全量解码。

**四、缺库必须降级而非报错**，这让本地开发与 CI 不必携带约 70MB 二进制。降级不是一档：**两个库都缺**时 `lookupGeo` 返回 `null`、收敛退回网段前缀、界面显示「位置未知」；只缺一个库时行为不同——缺 City 库时 ASN 仍有值，收敛落在 `asn:<asn>` 档（不是网段档），界面显示「位置未知」加运营商名；缺 ASN 库时收敛退回网段档，界面照常显示地名。这两种半加载态的收敛范围比全就绪时宽，所以 `GET /api/admin/request-logs/new-ips` 一并返回 `geoip: { city, asn }`，洞察页在任一缺失时显示提示条写明缺哪个库、退化到哪一档——否则用户只能从一片「位置未知」里猜是库没传还是功能没生效。

## 取舍

**这个决策主动降低了告警灵敏度。** 若 `AUTH_TOKEN` 泄露，且攻击者恰好从用户用过的同一运营商/机房、同一城市发起访问（例如同一家 VPS 厂商的另一台机器），将**不再触发告警**。

**盲区比「恰好」二字听起来大得多。** 一个已确认的 `asn:<n>|geo:<cityGeonameId>` 不是「一台机器」而是一整个地址集合，而用户主力网络恰是最宽的那类：`asn:9808|geo:<上海的 geoname_id>` 等价于「上海任意一台中国移动手机」，量级是百万级终端，买一张 SIM 卡即可落入，不需要任何巧合。用户最先确认掉的那个范围，往往正是最宽的那个。

**第二档退化后的语义更宽。** 城市缺失时城市限定被整条丢掉，一个已确认的 `asn:<n>` 等于该 ASN 的**全球**地址空间——例如 `asn:14061`（DigitalOcean）约 200 万个地址。用户开一次走 DO 出口的 VPN 并点了「知道了」，此后任何人租一台该厂商的机器访问都不再告警。而 GeoLite2-City 对云/托管段经常查不到 city，「经常开 VPN」正是这个决策的主场景，所以第二档不是罕见退路。

**确认是永久的：无 TTL、无复报。** `acknowledgeIpScope` 把 `acknowledged` 置 1 后，该 tier 下该范围此后永不再提醒，没有过期、没有周期性重新确认。**范围有多宽 × 静默有多久，两者相乘才是真实代价**，只看单次范围会低估。

**半加载态会让实际收敛档比上表更宽**（决策四）：只有 ASN 库就绪时，全部来源落在 `asn:<asn>` 这一最宽档；这不需要攻击，一次普通运维手滑（只上传了一个 mmdb）就会造成。因此就绪状态必须暴露到界面，而不是只写在文档里。

接受的理由：

- 本仓是单人自托管、非 SaaS（见 `AGENTS.md`「审查尺度」）。
- 原设计已明确「只提醒不拦截」，真正的防线是限流与令牌本身，此提醒从来不是访问控制。
- 高噪音提醒的实际安全价值是负的——它训练用户忽略告警。降低灵敏度换回「用户真的会看」，净收益为正。

**归属地是推测，不是定位。** 国家级准确率高，但城市级对家宽与手机流量常落到省会或邻市；对 VPN 与云机房 IP，返回的是 IP 段的注册地而非机器实际位置。界面已就此加免责声明，不可作为安全证据。

## 备选与否决

- **按纯 ASN 收敛**：噪音压得更干净（VPN 换节点 IP 也不报），但灵敏度更低。用户选了更紧的一档。
- **按 `/24` 收敛、不引入归属地库**：零依赖，但运营商 NAT 池经常跨 /24，只能压掉一部分噪音，且解决不了「看不懂是谁」。
- **ip2region 替代 GeoLite2**：国内 IP 有中文省市且体积小，但国外 IP 只到国家级、拿不到 ASN——用户开 VPN 时正好废在关键处。
- **在线归属地 API**：服务端要把来源 IP 外发给第三方，且有频率限制与可用性依赖。
- **GeoLite2 进镜像**：镜像 +约 70MB（City ≈ 60MB + ASN ≈ 9MB），每次 Watchtower 部署多传一次。
