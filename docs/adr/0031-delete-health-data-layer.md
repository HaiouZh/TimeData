# 0031 删除健康数据层：6 张表、6 个同步域与字段 schema 全清

## 状态

已采纳（2026-08-14）。部分取代 [ADR 0024](0024-retire-health-subsystem.md)——推翻的只是它的「保留数据层」，其「删除 UI 与采集管线」仍然有效。

## 背景

[ADR 0024](0024-retire-health-subsystem.md)（2026-07-29）退役了健康子系统的 UI 与采集管线，但**刻意保留**了数据层：6 张表（SQLite + Dexie）、`healthSchemas.ts` / `chartSchemas.ts`、`healthRows.ts` / `chartRows.ts`、6 个同步域与 backup bundled 角色。

保留的唯一理由是**协议兼容**，具体两条：老设备 push 上来会因未知域被拒收；备份文件里的健康段导入时会失去落点。结论是「删域是破坏性变更，收益不抵风险」。

半个月后复核这两条，两条都不成立。

## 核实

**「老设备 push 会被拒收」——机制属实且比原文更严重，但触发前提不存在。**

未知表名确实会让**整批 push 回 409、一条不落**（`routes/sync.ts` 的 `validation.valid` 分支：只要有一条 change 的 `tableName` 不在登记簿，整个批次 `appliedCount=0`）。ADR 0024 说的「拒收」被低估了。

但客户端**从来不产生健康域的变更**。健康数据由服务端 Python 子进程抓取后直接写库，客户端只在 pull 时接收；退役前客户端全部非测试代码里，这 6 张表只出现在 Dexie 声明、域登记、备份标签三处，**没有任何一处写入**。唯一曾由客户端产生的是 `health_charts`（用户配置的图表），而其配置面板在 ADR 0024 那次就已删除。没有生产者，就不会有待推送的健康 change，也就不会触发那个 409。

**「备份的健康段会失去落点」——不成立。**

`validateBackup` 遍历的是**当前**登记簿 `BACKUP_BUNDLED_DOMAINS`，按域名从备份文件里取键。备份文件里多出来的键**根本不会被读到**，静默忽略，不报错也不中断导入。老备份在删域之后仍能正常导入，只是其中的健康段不再落地——这正是期望行为，不是故障。

**真正不可逆的只有数据本身。** tag `retire/health` 保的是代码，不是数据。这条由 SQL 存档消化（见「决策」）。

## 决策

**删除健康数据层，三端代码、协议登记与库表全清。**

- shared：删 `healthSchemas.ts` / `chartSchemas.ts` 及其测试；`SYNC_DOMAINS` 从 16 域降到 10 域；`types.ts` 删 12 个静态判别联合成员。
- server：删 `healthRows.ts` / `chartRows.ts`、`health-charts.e2e.test.ts`；`domains.ts` 删 6 域；`schema.ts` 删 6 张表的建表语句；`reset.ts` / `backfillSeq.ts` 删表条目；9 个手写建表夹具同步清理。
- client：Dexie v17 用 `null` 删 6 个 store；`clientDomains.ts` 删 6 域，`BACKUP_BUNDLED_DOMAINS` 随之收窄。

**物理表由人工在生产库 DROP 一次，代码里不写任何 DDL。**

**删表前先把 6 张表 dump 成 SQL 存档**（服务器 `/opt/timedata/data/archive/` 与本地各一份，5511 条：心率 1191 / HRV 1190 / 睡眠 1248 / 压力 1191 / 跑步 688 / 图表配置 3）。存档把这件事从「不可逆决策」降级成「可回灌的机械操作」，因此不阻塞在 run-track 数据完整性的逐条核对上。

## 被否决的替代方案

1. **照抄 `known_ips` 的常驻 DDL**（在 `schema.ts` 建表段写 `DROP TABLE IF EXISTS health_*`，每次启动都跑）。否决：那句 DDL 的**自身注释已经承认它是债**——「这是一次性迁移，却写成了每次启动无条件执行的破坏性 DDL」，并警告此后任何人建同名表都会在下次重启被静默清空。服务端只有生产一个库，手工执行一次即永久完成；把一次性动作写成永久生效的破坏性语句，是拿一次省事换长期的脚下地雷。
2. **只删代码、物理表原样留着**。否决：代码收益与删干净完全相同，但库里会长期躺着 6 张再没有任何代码认识的表——没有 schema、没有映射、没有测试，只有下一个读库的人要花时间搞清它们是什么。存档已经提供了后悔药，不需要用死表再提供一次。
3. **引入一次性迁移账本机制**（记录迁移是否跑过，跑过就不再执行）。否决：为一个只执行一次的动作新建一层基础设施，YAGNI。
4. **维持 ADR 0024 的保留决策**。否决：见「核实」——它的两条理由一条前提不存在、一条经查完全不成立。在单人自用、所有设备可更新的前提下，那是没有对价的防御成本。

## 后果

- 同步域从 16 个降到 10 个。`syncDomains.test.ts` 新增一条封闭性护栏：任何健康域被加回登记簿都会先红一次。
- **备份格式不升版本**（仍是 `timedata.backup`）。删域收窄了语义但不破坏格式：老备份照常导入，健康段被静默忽略。这一条已写进 [backup](../evergreen/backup.md)。
- 客户端 Dexie 升到 v17。老库升级时 6 个 store 连同其中的本地数据一并删除，其余数据完好；有 v16→v17 迁移测试守着。
- 健康历史数据此后只存在于两处：SQL 存档、独立项目 run-track。TimeData 侧不再有任何副本。
- **「删域是破坏性协议变更」这条红线不因本 ADR 放宽**。它仍是默认立场，只是这一次红线后面没有真实的兼容性负担——判据是「有没有实际的生产者与消费者」，不是「登记簿里有没有这一行」。
- ADR 0024 的回溯点 tag `retire/health` 仍然有效，指向健康 UI 与采集管线俱在的最后状态。
