# 文档组织规则 · 拆分与体量

> [返回文档组织规则](../_docs-guide.md)。本文说明 evergreen 文档何时、沿哪个轴拆分，以及体量闸如何约束拆分；写什么、怎么组织和骨架见母文档，检查命令见 [检查与闭环](checks.md)。

## 1. 毕业阈值

通过 [母文档](../_docs-guide.md#docs-guide-s0) 后，文档撞 hard cap 时合法动作只有四个：删过时 / 越界内容（越界内容按母文档 §0.4 先补落点再 trim）、沿功能子域横切外提、沿读者路径纵切外提，或在长成独立主题时升格。后三者是结构安置动作：前两者是外提的两条轴，另一个是升格。外提前先判该走哪条：**能沿功能子域切的走横切；功能子域已切尽、剩下的是跨子域公共层（流程 / 不变量 / 速查 / 排障）的，走纵切。** 升格的准入与动作见 §1.3。

**判轴前先消歧**：本节的轴相对**代码归属边界**而言，横切 = 沿功能子域把归属切开（`covers` 跟着走），纵切 = 垂直于它、按读者路径切开（`covers` 不动）。母文档所称「横切关注点 / 层」（architecture、data-model 这类跨所有主题的层）是另一个词：跨全部子域的公共层在本文走的是纵切。判反了会去迁一片与母主题全交叉的 `covers`，只能靠切碎或复制硬凑，而门禁不会提示这种错切。

横切与纵切共用以下搬迁动作，只有准入判据不同。

1. 把内容移到当前母文档同名子目录的 `docs/evergreen/<路径>/<母>/<子>.md`。
2. 横切要迁走对应 `covers:`；纵切不迁，母文档 `covers` 不变。
3. 在子文档顶部回链当前母文档，并由母文档的「子文档索引」登记。
4. 重写链接与内部引用，再全仓扫入向引用；范围不只 `docs/`、`AGENTS.md`、`README.md`，脚本、测试、fixture、baseline 里编码的旧路径 / 锚点也要扫。
5. 对新子文档逐段重跑母文档 §0.5 / §0.5b：外提不是继承母文 `contracts` 了事，新落点里的清单、字段、数值、枚举或跨源不变量要重新决定挂 `contracts`、改源指针还是删除副本。
6. 运行 `node scripts/check-evergreen-docs.mjs --write-size-baseline` 重写 size baseline：新增子文档必须落基线；横切还要更新母文档迁走后的 covers 数，纵切母文档 covers 数不变。

architecture 只在升格到根主题层时登记，不下探子文档；升格另按 §1.3 办理。

相对链接必须按新目录深度重算：被搬走正文里的 `[x](todo/x.md)` 可能变成 `[x](../todo/x.md)`，`[x](x.md)` 可能变成 `[x](../x.md)`，`[ADR](../adr/x.md)` 在本目录变成 `../../adr/x.md`。不要照抄示例路径，先从新文件位置逐段回算。

`§x.y` 引用分四类，逐条判断后再动手：

| `§x.y` 的形态 | 它指谁 | 处置 |
|---|---|---|
| 紧跟在指向**别的文档**的链接后（`[tracks](../tracks.md#tracks-s5)`） | 那份文档的章节 | **章节号一个字不动**，只改链接路径 |
| **裸** `§x.y`（前面没有链接） | 母文档的章节 | 补前缀，例如 `[母文档](../<母>.md) §x.y` |
| 指向**本次正被搬走**的那几节 | 已迁到子文档 | 重指到子文档，且编号形态会变：原 `§3.4` 在子文档中改写成 `[子文档](x.md) 第 4 条` 或稳定小节名 |
| **入向**：仓库文件、以及母文档剩下的正文，指向**本次被搬走**的那几节 | 已迁到子文档 | 全仓搜索指向母文档的 `](<母>.md) §` 与裸 `§`，逐条重指到子文档的「第 N 条」或小节名；脚本测试、fixture 与 baseline 里的旧路径同样算 |

前三类在母文档与新文档中完成；第四类唯一需要跨仓库搜索，最容易整批漏掉。第一类也容易误判为母文档章节。`check:docs:links` 只检查 Markdown 链接目标的 `.md#id` 是否有严格配对的 `<a id="..."></a>` 显式锚点（两种合法落点见 [检查与闭环](checks.md)）；不检查同页 fragment、Markdown 标题自动锚点或 prose 的 `§x.y`，所以四类 prose 引用必须人工逐条核对。

锚点也吃体量预算：只给需要被外部稳定引用的小节补显式锚点，动手前先估算锚点税并确认 hard cap 余量覆盖它；余量不够时先按 §0.5b / 纵切释放空间，不能靠全量铺锚点把文档推过线。

同步域是横切样例：[sync](../sync.md) 索引 [sync/domain-registry](../sync/domain-registry.md)；纵切样例见下节。

### 1.1 横切：外提一个功能子域

只有子主题同时满足三条，才外提成独立子文档：

1. 它的 `covers:` 独立成簇，不与母主题其余部分交叉。
2. 体量过线：单文档 soft cap 约 15k 字符，hard cap 约 25k 字符；子主题段超过约 6k 字符时进入候选。
3. 它被独立编辑或引用，改它时通常不碰母主题其他段落。

这里的 `covers` 独立成簇只是拆分判轴 / 横切准入判据，不是全局「一文件只归一个主题」规则；全局多对多归属见 [母文档](../_docs-guide.md#docs-guide-s1-2)。

这些数字是治理参考值，不是机械铁律。三条一起满足，才说明拆出去会降低维护成本。母文档名下已有 **≥2 份横切子文档**时，横切轴多半已用尽，出路要往纵切找；`check:docs:size` 撞 hard cap 的报错会点名这类文档。纵切是否带 `covers` 取决于内容，不能仅凭 `covers` 非空把纯代码入口地图误判为横切。

搬迁步骤与四类引用处置均见 §1，尤其不可漏扫入向引用。

### 1.2 纵切：外提一条读者路径

横切的第一条件预设了拆分沿代码归属边界走。一个主题把功能子域切尽后，母文档剩下的是**跨全部子域的公共层**，它的 `covers` 与母主题全交叉，横切第一条件永远不可能满足，于是母文档卡在 hard cap 上无路可走。纵切是这种情况下的合法出路。

同时满足四条才外提：

1. **独立消费**：只读这一份能得到完整价值，不必回母文档补上下文。
2. **访问路径不同**：读它的时机与母文档主体不同。操作化问法是「这两节会不会在同一次任务里被一起读」：会，则同属一条路径、必须一起走；不会，才是两条路径。这同时圈定完整边界并防止滥拆。
3. **体量过线**：判据 2 圈出的**整条路径**超过约 6k 字符。量的不是单个 `###` 小节；例如模块速查的客户端、服务端与测试可能是同一条「找代码在哪」路径，必须整体判断。
4. **母文档移走后仍自足**：留下索引，读者不点开也知道有这条路径、何时该点。

触发词是「**混入**」，不是「太长」：解释被散落地混进其他章节，才说明应按读者路径切；访问路径不同先于体量过线，先圈边界再量体量。每个主题的纵切通常只产出 2–3 份。

陈述契约或不变量的纵切子文档可使用：

```yaml
---
type: evergreen
title: <主题> · <路径名>
covers:
contracts:
  - <schema / 登记簿>
last-reviewed: YYYY-MM-DD
---
```

纯代码入口地图在 `covers` 列正文实际指向的精确入口，`contracts` 留空或省略；其他纵切文档零 `covers` 时必须有 `contracts`。两个字段的冒号后都不能跟字符，`covers: []`、`contracts: []` 和行尾注释都会被解析成标量并由 size 闸拦下。`covers` 与 `contracts` 双空同样失败；完整规则见 [检查与闭环](checks.md)。

### 1.3 升格：长成主题，就往上一层走

同时满足三条才升格为主题：

1. 经母文档 §0.5 / §0.5b 筛过后仍超过 soft cap，不是靠删副本或缩措辞才显得大。
2. 它有独立的承上启下，能自己回答「是什么、怎么运作、边界在哪」，且它 `covers` 的那片代码与兄弟子文档不交叉。
3. 它自己仍需要再拆，能看出至少两个功能子域或读者路径；这才是升格的实质理由。

第三条只证明“这一层级已经装不下它”，不等于本次任务必须继续拆下去。升格可以只建立新主题与目录，把后续横切 / 纵切路径留给同一轮 plan 后续步骤或下一轮用户决策；是否立刻拆，取决于本轮目标和风险，而不是升格动作自动触发。

升格按六步办理：

1. 移到上一层，按需建立自己的目录。
2. 按实际层级登记：升到根主题层才在 [architecture](../architecture.md#architecture-s6) 登记为主题；更深层每升一级，由上一层主题或子主题在自己的索引登记，architecture 不下探。
3. 把母文档的子文档索引改成承上启下的邻居链接。
4. 重写所有相对链接；例如从 `<母>/<子>.md` 升到根主题层时，`../x.md` 变 `x.md`、`../../adr/x.md` 变 `../adr/x.md`。更深层必须按实际深度重算。
5. 全仓扫描入向引用，按 §1 的四类分别处置；脚本、测试、fixture、baseline 中的旧路径 / 旧锚点也必须纳入。
6. 重写 size baseline，并核对输出的抬高、新增、移除与收窄清单。

母文档的 `covers` 不动，因为升格前那片 `covers` 已在子文档身上并随文件走；升格改变导航层级和入口关系，不借机扩大或收缩母主题管辖。

## 2. 体量闸：字符走绝对上限，covers 走棘轮

`pnpm check:docs:size` 先守 frontmatter 形状，再守体量与管辖；字符数不做棘轮，正文增长只在单文档真的膨胀到上限时才拦。

- **frontmatter 形状是硬闸**：evergreen 只接受 `type`、`title`、`last-reviewed` 三个必填标量，以及 `covers`、`contracts` 两个可选列表；未知键、缺必填键、列表写成标量都会失败。ADR 不参与这条形状校验。
- **机检闸存在是 no-gate**：evergreen 不能 `covers` 与 `contracts` 双空。横切文档至少有 `covers`；纯代码入口地图列精确 `covers`；零 covers 的纵切文档必须有 `contracts`。coverage 豁免只给测试基建、mock/fixture、纯转发 shim 或无隐藏契约的通用 helper，不能当成“暂不归属”的安置方式。
- **字符数是绝对上限，不是基线棘轮**：超过 hard cap（约 25000 字符）才报错，含义是「这篇太长了，该拆」。合法动作仍只有四个：删过时 / 越界内容（先按母文档 §0.4 补落点再 trim）、横切、纵切、升格；压缩措辞、删例子、把句子改短不是合法动作，四条都走不通就停下询问。超过 soft cap（约 15000 字符）只软提示，提示在超过 15000、20000、23000 字符时依次升级，边界是严格大于。
- **`covers` 数是棘轮**：`scripts/evergreen-size-baseline.json` 只记每篇文档的 `covers` 数与存在性。数目比基线大即报错，防止悄悄扩大管辖；字符数不记入基线。
- 基线必须覆盖当前全部 evergreen 文档；新增、删除或重命名 evergreen 文档而未更新基线都会失败。
- ADR 是决策记录，只追加，不参与体量闸。

真实职责扩展而要扩大 `covers` 时，运行 `node scripts/check-evergreen-docs.mjs --write-size-baseline` 并在提交信息说明原因。这个命令整体重写 filePath 到 covers 的完整映射，会把工作树中全部 covers 变化一起收编；因此写完必须看输出的 ⚠️ 清单，只保留本次应有的抬高、新增、移除和收窄。其他改动说明重写得过早，应先提交或还原无关变更。字符增长不需要重写基线。
