# 文档组织规则

> 这份文档讲 evergreen 文档**该写什么 / 不该写什么**（§0）、怎么组织（§1）和主题骨架（§2）。拆分 / 体量见 [_docs-guide/splitting.md](_docs-guide/splitting.md)，检查闭环见 [_docs-guide/checks.md](_docs-guide/checks.md)。
> 它不承载业务域细节；具体代码入口和数据流仍回到各域文档。

## 0. 内容边界与写作粒度：evergreen 只写「现在是什么」

**evergreen 是让人和 agent 都不用瞎找的那份东西**：告诉他该去哪，以及到了那儿也看不出来的事；写多细看有没有闸（§0.5b），装不下按 [拆分与体量](_docs-guide/splitting.md) 往下开一层。

**这是写 evergreen 之前的先决判据——先过 §0，再看组织、拆分与检查规则。** §1–§2 解决「放哪、长什么样」；[拆分与体量](_docs-guide/splitting.md) 解决「多大该拆、怎么拆」；[检查与闭环](_docs-guide/checks.md) 解决「本地 / CI 怎么守」。§0 解决「这段内容该不该进 evergreen」。它是写入口的规则，不是事后校验：内容一旦写错层，后面的组织规则和体量闸都救不回来（错位的段落照样合规，只是把 hard cap 额度花在了别层的内容上）。

一份 evergreen 文档回答的是**「系统现在是什么样、有什么功能、机制怎么运作」**。四层各答一个问题，不重叠：

| 层 | 回答什么 | 位置 |
|---|---|---|
| **evergreen** | **现在是什么样 / 有什么功能 / 机制怎么运作** | `docs/evergreen/**` |
| ADR | 为什么选了这条路（含被否决的路、当时的权衡） | `docs/adr/**` |
| AGENTS.md | 怎么操作这个仓库 + 对 agent 动作的授权边界 | `AGENTS.md`（面向人的部署 / 运行入口在 `README.md`） |
| 本地过程文档 | 正在做什么 / 做过什么 | `docs_local/**`（不入 Git） |

### 0.1 准入：这些进 evergreen

- **机制与数据流**：端到端怎么跑、哪个模块负责哪一段。
- **字段级契约**：schema、SQL ↔ JS 映射、同步域登记、默认值。
- **不变量 / 红线**：陈述式的「系统恒满足 X」「Y 永不成立」。
- **边界**：本主题不引用什么、不参与什么。
- **模块速查与测试落点**。
- **结论式因由锚**：一句「这是有意的，因为 …」+ ADR 链接。**只写结论，不复述论证**——它防的是把有意设计当 bug「修」掉，属于行为契约的一部分。

### 0.2 排除：这些不进 evergreen

| 越界内容 | 一眼认出的症状 | 归谁 |
|---|---|---|
| 决策论证、备选方案对比、当时的权衡 | 「考虑过 A，因为 … 选了 B」「取舍是 …」 | ADR |
| 对 agent 的动作指令与授权 | 祈使句：「改前先确认」「未经批准不改」「不当 bug 修」「先停手」 | AGENTS.md |
| 变更流水、时间线、「本轮改动」 | 带日期的记录、`<!-- 复核 … -->` 注释（见 §0.3） | 提交信息（历史归 git，不归文档正文） |
| 进行中的计划 / 待排期缺口 / 「本期未做」清单 | 「下一步」「待做」「一律不做」「真要补优先做 X」 | 活的进 `docs_local/ROADMAP.md`，攒着的进 `docs_local/backlog.md` |
| 阶段与批次叙事 | 「T3 提供 …」「Phase 1 收口」「阶段三返工两次」 | 提交历史 / `ROADMAP-archive.md`；正文只留最终形态 |
| 仓库操作纪律 | 怎么提交、开哪个 worktree、跑哪个门禁 | AGENTS.md（工具链**机制**可留 [development](development.md)，纪律句归 AGENTS.md） |

**判据一句话**：一句话若**在没有任何改动发生时也成立**，它描述现状 → 进 evergreen；若它只在「有人正要改代码」时才有意义（指令、授权、当时的取舍） → 不进 evergreen。

**一个有意的例外——领域自带的准入流程留在领域文档里**：像「新增颜色层级必须用户拍板」（[design-language](design-language.md) §1）、「新增同步域要走登记簿 checklist」（[sync/domain-registry](sync/domain-registry.md)）这类授权，虽是祈使语气，但强绑定该领域机制、且改这块的人一定在读这份文档——放这里比放 AGENTS.md 更可能被读到。判据：**它是这个领域特有的准入步骤（留下）**，还是**跨领域通用的动作纪律（归 AGENTS.md）**。「已排期区不接 dnd 系统」这种是排期决定，两者都不是，归 backlog。

**「不做什么」有两种，别混**：「本域不引用分类表」是**当前边界**（进 evergreen）；「项目级重力一律不做」是**排期决定**（进 backlog）。前者描述系统形状，后者描述人的打算。

### 0.3 `<!-- 复核 -->` 注释：不写

**别在文档里累积 `<!-- 复核 YYYY-MM-DD（xxx）：本轮改了 … / 本轮不影响 … -->` 这类注释。** 三个理由：

- 没有任何脚本消费它，`last-reviewed` 字段已经承载「复查到哪天」；
- 它记的是历史，evergreen 只描述现状——改动记录归提交信息；
- 它吃 hard cap 额度：todo.md 曾被 5 条这样的注释占掉 681 字符，而当时距 hard cap 只剩 1156 字符。

复查文档要做的只有两件事：**改正文 + 更新 `last-reviewed`**。若复查确认「这轮改动没影响本文」，**什么都不写**——不留痕即结论。遇到既存注释：信息已在正文的直接删；信息不在正文的先并进正文再删。

删掉不等于丢掉——这类信息本来就各有归处，只是没人往那儿放：**改了什么** → `git log`；**为什么这么改** → ADR；**什么时候做 / 还没做** → `docs_local/ROADMAP.md` 与 `backlog.md`；**怎么部署运行** → README。注释是这四个地方都懒得开时的堆放处。

### 0.4 越界了怎么办：先补落点，再 trim

发现 evergreen 里有越界内容**别就地删**（与 [AGENTS.md](../../AGENTS.md)「文档 / 变更日志」节里反向那条规则对称）：先确认目标层是否已清楚承载（ADR 有没有那条决策？AGENTS.md 有没有那条授权？），没有就先补上，再把 evergreen 里那段 trim 成「一句现状 + 指针」。信息不能在搬运中丢。

搬运时**优先并进正文而不是另起一段**：注释、脚注、附录形态的信息不会被后来人读进正文，正文里的断言就会跟它打架。真实案例：[security](security.md) 正文长期断言本地 UI 偏好 key「不存 Token、任务正文或其他业务内容」，而反例 `quickNoteComposerDraft`（用户未发出的速记正文）只写在一条复核注释里——注释在，正文的断言却是错的。

### 0.5 详略之一：只写 grep 不出来的，其余只指路

一句话判据：**一段若能靠一条 grep 或打开一个文件得到，只留锚点。** 这是默认规则。唯一允许抄全的例外是 §0.5b 第 1 档：字段、枚举、清单的源文件已在本文 `contracts`，strict 会逼复查，因此可以抄全。agent 的成本不是读得慢，而是不知道该 grep 什么；跨文件、跨包或有意不对称的结论才需要文档先把搜索词和关系说出来。

| | 写什么 / 不写什么 | 原因 |
|---|---|---|
| **写** | 跨包隐式耦合；不变量 / 红线；踩坑与表现；有意例外 / 两端不对称；结论式因由锚 + ADR；事实源文件 | 不知道该从哪个词、哪个包或哪个反例开始找，单开一个文件也得不到结论 |
| **不写** | 完整字段 / prop / 函数签名；逐行复述单文件；className / UI 原文；类型直接可读字段 | 一条定位式 grep 或打开源文件即可得到，文档副本只会先腐烂 |

要消灭的是**探索式 grep**：读者还不知道该找什么，只能在仓库里盲搜；不消灭**定位式 grep**：文档给出文件、概念或锚点后，读者据此直达源头。文档不应成为代码的完整副本。

### 0.5b 详略之二：抄不抄清单，由有没有闸决定

详细度由有没有闸决定，不由重要性决定。清单、字段表或枚举一旦脱离源文件，就必须按下表选一档：

| 档 | 源文件与本文关系 | 动作 |
|---|---|---|
| 1 | 源文件在本文 `contracts` | 可抄全；字段级 schema 表正当用在这一档，因为它把字段语义接到了 strict 闸上 |
| 2 | 源文件不在本文 `contracts` | 二选一：把源文件挂进 `contracts`，或改成指向源文件的锚点；不许两头不做 |
| 3 | 没有源文件可挂的派生 / 汇总清单（典型是目录结构、文档清单、文件系统自己能算出来的清单） | 额外副本只能删；architecture 登记簿表和主题文档的子文档索引是权威导航入口，可保留。禁止额外复述「当前有哪些子文档 / 主题」的可计算汇总 |

没有变更闸的清单仍会腐烂：例如 architecture 的 health 已退役却仍留在登记簿，或 diary / goals 已有新子文档而主题索引没有跟上。它们不是不重要，而是复制出的清单没有让来源变化时强迫复查。

### 0.6 抗过时的三条写法

1. **禁时间性措辞**：不写「目前 / 暂时 / 最近 / 本轮 / 新增了 / 已改为 / 待补」。这类词把写作时刻锚进正文，而下一次改动**没人会回来撤它**，句子于是自动变假。写「X 是 Y」，不写「X 已改为 Y」；「新增 `sessionId` 字段」→「`sessionId`：反挂手头会话，默认 null」。变化本身归 ADR 与提交历史。
2. **一处真相**：同一事实只在一处展开，别处只留链接（这是 §1.2 单轴归属在**事实级**的同一条规则）。重复的第二份必然先腐烂——改代码的人只会改他搜到的那一处。
3. **清单按闸处理**：正文若要抄某文件里的具体清单 / 数值 / 枚举（域优先级、settings key 表、SQL 列名），按 §0.5b 选档：挂进 `contracts` 才可抄全；不愿意挂就改成「见 `xxx.ts`」的指针；无源可挂的清单只能删。

### 0.7 什么才算「复查过」——才能动 `last-reviewed`

`last-reviewed` 声明的是「有人逐段核对过代码」，不是「有人动过这个文件」。

- **复查 = 逐段问「这句现在还真吗」，并打开 `contracts` 列的文件核对**。只删注释、只改措辞、只调格式**不算**复查，别顺手 bump `last-reviewed`——bump 了就等于对下一个人撒谎，让 `check:docs:stale` 失去意义。
- 某段**说不清它对应哪段代码**时，它要么已过时、要么本就不该写：删掉，或补 `covers` 让它有主。别留着当装饰。
- 发现新事实与既有段落冲突：**改写原句**，不在文末追加一段。「另外 / 此外 / 补充说明」通常是叠加痕迹——两句话打架时读者只会更糊，而先腐烂的那句往往是旧的那句。

## 1. 组织主轴：按主题

长期文档按**主题**组织。主题 = 任何值得作为独立单元导航、且 `covers` 能成簇的话题。主题不限于数据域，可沿不同轴切分：

- **数据/能力域**：端到端拥有一个数据/能力域，跨包覆盖该域全部代码，例如 sync、backup、timeline、todo、quick-notes、health、stats-insights、categories-settings。
- **模块/功能**：一个跨包的具体功能或子系统（做深之后值得单独成篇，方便分模块查代码）。
- **设计语言**：控件库、配色 / token、按钮与组件规范、图标、字体等可复用的视觉/交互规范（不绑定任何单一功能）。
- **横切关注点/层**：跨所有主题的层，例如 architecture、data-model、development、deployment、security、cli。

判定不是“它是不是域”，而是**“它能不能成为一个聚焦、`covers` 成簇、可独立维护的主题”**。新增文档先走两问：

1. 它能成为一个聚焦、`covers` 成簇、可独立维护的主题吗？是 → 新建主题文档（或归入已有主题、作其子文档）。
2. 它只是某个已有主题的细节，或跨所有主题的层吗？是 → 并入最贴近的现有主题 / 横切文档，不另建同级文件。

文档组织不按包切。TimeData 的功能通常纵向穿过 client、server、shared、cli；按包切会让读者自己拼数据流，也会把 `covers:` 退化成整包级别。

## 1.1 层级递归：地图 → 主题 → 子文档 → …

evergreen 的层级递归向下，不设层数上限；每一级都只索引下一级，所以永远有下一层可开：

```text
architecture.md（地图）               只索引根主题
  └─ <主题>.md（根主题）              拥有主题边界，并索引子文档；目标 < 15k 字符
       └─ <主题>/<子>.md（子文档）    沿功能子域或读者路径继续外提
            └─ <主题>/<子>/<孙>.md    每一级都按同一规则继续
```

- **地图（architecture）**：只列根主题与横切文档登记簿，不索引子文档、不展开域字段细节。
- **主题文档**：主题的稳定入口，承上启下，承载核心契约 / 不变量，并索引自己的子文档；目标控制在 ~15k 字符以内。
- **子文档**：母文档是 `docs/evergreen/<路径>/<母>.md` 时，子文档放在同名子目录的 `docs/evergreen/<路径>/<母>/<子>.md`；根主题只是 `<路径>` 为空的特例。它是完整 evergreen：`type` / `last-reviewed` 必填，顶部以 `../<母>.md` 回链当前母文档，并由当前母文档索引；横切 / 纵切 / 升格判据与动作见 [拆分与体量](_docs-guide/splitting.md)。

## 1.2 `covers`：主题级单轴归属

文件的显式主题归属只归一个主题目录；同一主题目录内可有多份文档 `covers` 同一文件，跨主题则互斥。可复用控件 / token 归设计语言主题，功能专属组件归功能主题；其他主题靠「承上启下 · 邻居」链接，不重复正文。

跨主题互斥只禁止**同一文件被两个主题显式声明**。一边用 glob、另一边在升格主题中显式点名，可以共存：例如 todo 以 glob 认领其目录时，project-zone 主题可显式列 `TodoProjectSection`；这是主题升格中的有意重叠，不是把同一文件归给两个主题。

## 1.3 `covers` 归属 vs `contracts` 契约点（谁触发 strict）

frontmatter 里两个字段分工不同，别混用：

| 字段 | 含义 | 触发 strict？ | 谁消费 |
|---|---|---|---|
| `covers` | **纯归属声明**：这片 glob 下的代码归本文档讲 | **否** | coverage（新代码必有主人）、warn（软提示可能受影响的文档）、size（covers 数走棘轮） |
| `contracts` | 「**改这个文件、不改文档，文档一定错**」的契约级集合（schema / 登记簿 / API 面 / token 定义） | **是** | strict（改契约文件却没同步文档就报红） |

为什么要拆：`covers` 为了 coverage 铺得很宽（常含整目录 `**`），若拿它触发 strict，改域里任何一个 helper、改个措辞都逼你动文档——假阳性。`contracts` 把「碰它文档必错」的那一小撮单独拎出来，strict 只认它，从「碰这个域就逼改文档」收窄成「碰真正的契约点才逼改文档」。

判据一句话：**「改这个文件而不改文档，文档一定错」才进 `contracts`**。典型进 `contracts` 的：`*Schemas.ts`、`syncDomains.ts` / `sync/domains.ts`（域登记簿）、`db/schema.ts`、`types.ts` 里被文档钉死字段的类型、API 路由契约、`index.css` token、控件目录 `ui/**`。纯实现文件、内部 helper 只进 `covers` 不进 `contracts`。

**`contracts` 与 `covers` 各自独立，不构成子集关系，绝不加子集校验。** `covers` 声明「这片代码归本文档讲」，`contracts` 声明「改这个文件本文档一定错」。多数文档的 `contracts` 确实取自它的 `covers`，但那是常见情形不是约束；加子集校验会把纵切与升格焊死。

每份 evergreen 的 `covers` / `contracts` 至少有一个非空，这是 no-gate：纵切且没有代码时用 `contracts`，纯代码入口地图用精确 `covers`。一份文档可以没有 `contracts`（如 development、stats-insights）——说明它没有「改某文件必错」的硬契约点，strict 对它天然是 no-op，这是诚实状态，不是漏配。共享契约文件（`syncDomains.ts`、`entitySchemas.ts` 等）可同时进多份文档的 `contracts`，等价于「改它 → 复查所有把它当契约的文档」，有意为之。

## 2. 主题文档骨架

新建主题文档默认使用这个稳定头（数据域用“数据流/Schema”，设计语言/模块主题可把 §1/§2 换成“规范/构成”等更贴切的小节名，但「承上启下」必留）。**逐节填之前先过 §0 内容边界**：每段都要能通过「没有改动发生时也成立」这一问。

```markdown
---
type: evergreen
title: <主题>
covers:
  - <本主题端到端代码路径>
contracts:
  - <schema / 登记簿 / API 面>
last-reviewed: YYYY-MM-DD
---

# <主题>
> 一句话定位 + 讲什么 / 不讲什么
<!-- 只写现状：机制 / 契约 / 不变量 / 边界。决策论证归 ADR，对 agent 的指令与授权归 AGENTS.md，
     改动流水归提交信息，在办事项归 docs_local。
     不写「目前 / 本轮 / 新增了 / 已改为」这类时间性措辞；一条 grep 或打开一个文件能得到的（prop 清单、
     className、函数签名）也不写。判据见 _docs-guide §0。此注释填完可删。 -->
```
