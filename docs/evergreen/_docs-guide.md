# 文档组织规则

> 这份文档讲 evergreen 文档**该写什么 / 不该写什么**（§0），以及怎么组织、何时新建、写到多大该外提（§1 起）。
> 它不承载业务域细节；具体代码入口和数据流仍回到各域文档。

## 0. 内容边界与写作粒度：evergreen 只写「现在是什么」

**evergreen 是让人和 agent 都不用瞎找的那份东西**：告诉他该去哪，以及到了那儿也看不出来的事；写多细看有没有闸（§0.5b），装不下往下开一层（§3）。

**这是写 evergreen 之前的先决判据——先过 §0，再看 §1 起的组织与体量规则。** §1–§5 解决「放哪、多大该拆」；§0 解决「这段内容该不该进 evergreen」。它是写入口的规则，不是事后校验：内容一旦写错层，后面的组织规则和体量闸都救不回来（错位的段落照样合规，只是把 hard cap 额度花在了别层的内容上）。

一份 evergreen 文档回答的是**「系统现在是什么样、有什么功能、机制怎么运作」**。四层各答一个问题，不重叠：

| 层 | 回答什么 | 位置 |
|---|---|---|
| **evergreen** | **现在是什么样 / 有什么功能 / 机制怎么运作** | `docs/evergreen/**` |
| ADR | 为什么选了这条路（含被否决的路、当时的权衡） | `docs/adr/**` |
| AGENTS.md | 怎么操作这个仓库 + 对 agent 动作的授权边界 | `AGENTS.md`（面向人的部署 / 运行入口在 `README.md`） |
| 本地过程文档 | 正在做什么 / 做过什么 | `docs_local/**`（不入 Git） |

### 0.1 准入：这些进 evergreen

- **机制与数据流**：端到端怎么跑、哪个模块负责哪一段。
- **字段级契约**：schema、SQL ↔ JS 映射、同步域登记、默认值。
- **不变量 / 红线**：陈述式的「系统恒满足 X」「Y 永不成立」。
- **边界**：本主题不引用什么、不参与什么。
- **模块速查与测试落点**。
- **结论式因由锚**：一句「这是有意的，因为 …」+ ADR 链接。**只写结论，不复述论证**——它防的是把有意设计当 bug「修」掉，属于行为契约的一部分。

### 0.2 排除：这些不进 evergreen

| 越界内容 | 一眼认出的症状 | 归谁 |
|---|---|---|
| 决策论证、备选方案对比、当时的权衡 | 「考虑过 A，因为 … 选了 B」「取舍是 …」 | ADR |
| 对 agent 的动作指令与授权 | 祈使句：「改前先确认」「未经批准不改」「不当 bug 修」「先停手」 | AGENTS.md |
| 变更流水、时间线、「本轮改动」 | 带日期的记录、`<!-- 复核 … -->` 注释（见 §0.3） | 提交信息（历史归 git，不归文档正文） |
| 进行中的计划 / 待排期缺口 / 「本期未做」清单 | 「下一步」「待做」「一律不做」「真要补优先做 X」 | 活的进 `docs_local/ROADMAP.md`，攒着的进 `docs_local/backlog.md` |
| 阶段与批次叙事 | 「T3 提供 …」「Phase 1 收口」「阶段三返工两次」 | 提交历史 / `ROADMAP-archive.md`；正文只留最终形态 |
| 仓库操作纪律 | 怎么提交、开哪个 worktree、跑哪个门禁 | AGENTS.md（工具链**机制**可留 [development](development.md)，纪律句归 AGENTS.md） |

**判据一句话**：一句话若**在没有任何改动发生时也成立**，它描述现状 → 进 evergreen；若它只在「有人正要改代码」时才有意义（指令、授权、当时的取舍） → 不进 evergreen。

**一个有意的例外——领域自带的准入流程留在领域文档里**：像「新增颜色层级必须用户拍板」（[design-language](design-language.md) §1）、「新增同步域要走登记簿 checklist」（[sync/domain-registry](sync/domain-registry.md)）这类授权，虽是祈使语气，但强绑定该领域机制、且改这块的人一定在读这份文档——放这里比放 AGENTS.md 更可能被读到。判据：**它是这个领域特有的准入步骤（留下）**，还是**跨领域通用的动作纪律（归 AGENTS.md）**。「已排期区不接 dnd 系统」这种是排期决定，两者都不是，归 backlog。

**「不做什么」有两种，别混**：「本域不引用分类表」是**当前边界**（进 evergreen）；「项目级重力一律不做」是**排期决定**（进 backlog）。前者描述系统形状，后者描述人的打算。

### 0.3 `<!-- 复核 -->` 注释：不写

**别在文档里累积 `<!-- 复核 YYYY-MM-DD（xxx）：本轮改了 … / 本轮不影响 … -->` 这类注释。** 三个理由：

- 没有任何脚本消费它，`last-reviewed` 字段已经承载「复查到哪天」；
- 它记的是历史，evergreen 只描述现状——改动记录归提交信息；
- 它吃 hard cap 额度：todo.md 曾被 5 条这样的注释占掉 681 字符，而当时距 hard cap 只剩 1156 字符。

复查文档要做的只有两件事：**改正文 + 更新 `last-reviewed`**。若复查确认「这轮改动没影响本文」，**什么都不写**——不留痕即结论。遇到既存注释：信息已在正文的直接删；信息不在正文的先并进正文再删。

删掉不等于丢掉——这类信息本来就各有归处，只是没人往那儿放：**改了什么** → `git log`；**为什么这么改** → ADR；**什么时候做 / 还没做** → `docs_local/ROADMAP.md` 与 `backlog.md`；**怎么部署运行** → README。注释是这四个地方都懒得开时的堆放处。

### 0.4 越界了怎么办：先补落点，再 trim

发现 evergreen 里有越界内容**别就地删**（与 [AGENTS.md](../../AGENTS.md)「文档 / 变更日志」节里反向那条规则对称）：先确认目标层是否已清楚承载（ADR 有没有那条决策？AGENTS.md 有没有那条授权？），没有就先补上，再把 evergreen 里那段 trim 成「一句现状 + 指针」。信息不能在搬运中丢。

搬运时**优先并进正文而不是另起一段**：注释、脚注、附录形态的信息不会被后来人读进正文，正文里的断言就会跟它打架。真实案例：[security](security.md) 正文长期断言本地 UI 偏好 key「不存 Token、任务正文或其他业务内容」，而反例 `quickNoteComposerDraft`（用户未发出的速记正文）只写在一条复核注释里——注释在，正文的断言却是错的。

### 0.5 详略之一：只写 grep 不出来的，其余只指路

一句话判据：**一段若能靠一条 grep 或打开一个文件得到，只留锚点。** 这是默认规则。唯一允许抄全的例外是 §0.5b 第 1 档：字段、枚举、清单的源文件已在本文 `contracts`，strict 会逼复查，因此可以抄全。agent 的成本不是读得慢，而是不知道该 grep 什么；跨文件、跨包或有意不对称的结论才需要文档先把搜索词和关系说出来。

| | 写什么 / 不写什么 | 原因 |
|---|---|---|
| **写** | 跨包隐式耦合；不变量 / 红线；踩坑与表现；有意例外 / 两端不对称；结论式因由锚 + ADR；事实源文件 | 不知道该从哪个词、哪个包或哪个反例开始找，单开一个文件也得不到结论 |
| **不写** | 完整字段 / prop / 函数签名；逐行复述单文件；className / UI 原文；类型直接可读字段 | 一条定位式 grep 或打开源文件即可得到，文档副本只会先腐烂 |

要消灭的是**探索式 grep**：读者还不知道该找什么，只能在仓库里盲搜；不消灭**定位式 grep**：文档给出文件、概念或锚点后，读者据此直达源头。文档不应成为代码的完整副本。

### 0.5b 详略之二：抄不抄清单，由有没有闸决定

详细度由有没有闸决定，不由重要性决定。清单、字段表或枚举一旦脱离源文件，就必须按下表选一档：

| 档 | 源文件与本文关系 | 动作 |
|---|---|---|
| 1 | 源文件在本文 `contracts` | 可抄全；字段级 schema 表正当用在这一档，因为它把字段语义接到了 strict 闸上 |
| 2 | 源文件不在本文 `contracts` | 二选一：把源文件挂进 `contracts`，或改成指向源文件的锚点；不许两头不做 |
| 3 | 没有源文件可挂的派生 / 汇总清单（典型是目录结构、文档清单、文件系统自己能算出来的清单） | 额外副本只能删；architecture 登记簿表和主题文档的子文档索引是权威导航入口，可保留。禁止额外复述「当前有哪些子文档 / 主题」的可计算汇总 |

没有变更闸的清单仍会腐烂：例如 architecture 的 health 已退役却仍留在登记簿，或 diary / goals 已有新子文档而主题索引没有跟上。它们不是不重要，而是复制出的清单没有让来源变化时强迫复查。

### 0.6 抗过时的三条写法

1. **禁时间性措辞**：不写「目前 / 暂时 / 最近 / 本轮 / 新增了 / 已改为 / 待补」。这类词把写作时刻锚进正文，而下一次改动**没人会回来撤它**，句子于是自动变假。写「X 是 Y」，不写「X 已改为 Y」；「新增 `sessionId` 字段」→「`sessionId`：反挂手头会话，默认 null」。变化本身归 ADR 与提交历史。
2. **一处真相**：同一事实只在一处展开，别处只留链接（这是 §1.2 单轴归属在**事实级**的同一条规则）。重复的第二份必然先腐烂——改代码的人只会改他搜到的那一处。
3. **清单按闸处理**：正文若要抄某文件里的具体清单 / 数值 / 枚举（域优先级、settings key 表、SQL 列名），按 §0.5b 选档：挂进 `contracts` 才可抄全；不愿意挂就改成「见 `xxx.ts`」的指针；无源可挂的清单只能删。

### 0.7 什么才算「复查过」——才能动 `last-reviewed`

`last-reviewed` 声明的是「有人逐段核对过代码」，不是「有人动过这个文件」。

- **复查 = 逐段问「这句现在还真吗」，并打开 `contracts` 列的文件核对**。只删注释、只改措辞、只调格式**不算**复查，别顺手 bump `last-reviewed`——bump 了就等于对下一个人撒谎，让 `check:docs:stale` 失去意义。
- 某段**说不清它对应哪段代码**时，它要么已过时、要么本就不该写：删掉，或补 `covers` 让它有主。别留着当装饰。
- 发现新事实与既有段落冲突：**改写原句**，不在文末追加一段。「另外 / 此外 / 补充说明」通常是叠加痕迹——两句话打架时读者只会更糊，而先腐烂的那句往往是旧的那句。

## 1. 组织主轴：按主题

长期文档按**主题**组织。主题 = 任何值得作为独立单元导航、且 `covers` 能成簇的话题。主题不限于数据域，可沿不同轴切分：

- **数据/能力域**：端到端拥有一个数据/能力域，跨包覆盖该域全部代码，例如 sync、backup、timeline、todo、quick-notes、health、stats-insights、categories-settings。
- **模块/功能**：一个跨包的具体功能或子系统（做深之后值得单独成篇，方便分模块查代码）。
- **设计语言**：控件库、配色 / token、按钮与组件规范、图标、字体等可复用的视觉/交互规范（不绑定任何单一功能）。
- **横切关注点/层**：跨所有主题的层，例如 architecture、data-model、development、deployment、security、cli。

判定不是“它是不是域”，而是**“它能不能成为一个聚焦、`covers` 成簇、可独立维护的主题”**。新增文档先走两问：

1. 它能成为一个聚焦、`covers` 成簇、可独立维护的主题吗？是 → 新建主题文档（或归入已有主题、作其子文档）。
2. 它只是某个已有主题的细节，或跨所有主题的层吗？是 → 并入最贴近的现有主题 / 横切文档，不另建同级文件。

文档组织不按包切。TimeData 的功能通常纵向穿过 client、server、shared、cli；按包切会让读者自己拼数据流，也会把 `covers:` 退化成整包级别。

## 1.1 层级递归：地图 → 主题 → 子文档 → …

evergreen 的层级递归向下，不设层数上限；每一级都只索引下一级，所以永远有下一层可开：

```text
architecture.md（地图）       只索引主题
  └─ <主题>.md（主题）        拥有主题边界，并索引子文档；目标 < 15k 字符
       └─ <主题>/<子>.md（子文档） 沿功能子域或读者路径继续外提
            └─ …              长成主题形状后升格，获得自己的目录
```

- **地图（architecture）**：只列主题与横切文档登记簿，不索引子文档、不展开域字段细节。
- **主题文档**：主题的稳定入口，承上启下，承载核心契约 / 不变量，并索引自己的子文档；目标控制在 ~15k 字符以内。
- **子文档**：放在 `docs/evergreen/<主题>/<子主题>.md`，沿功能子域或读者路径继续外提。它是完整 evergreen：`type` / `last-reviewed` 必填，顶部以 `../<主题>.md` 回链母主题；横切 / 纵切的选择见 §3。长成主题形状后，按 §3.3 升格并获得目录。

## 1.2 `covers`：主题级单轴归属

文件只归一个主题目录；同一主题目录内可有多份文档 `covers` 同一文件，跨主题则互斥。可复用控件 / token 归设计语言主题，功能专属组件归功能主题；其他主题靠「承上启下 · 邻居」链接，不重复正文。

跨主题互斥只禁止**同一文件被两个主题显式声明**。一边用 glob、另一边在升格主题中显式点名，可以共存：例如 todo 以 glob 认领其目录时，project-zone 主题可显式列 `TodoProjectSection`；这是主题升格中的有意重叠，不是把同一文件归给两个主题。

## 1.3 `covers` 归属 vs `contracts` 契约点（谁触发 strict）

frontmatter 里两个字段分工不同，别混用：

| 字段 | 含义 | 触发 strict？ | 谁消费 |
|---|---|---|---|
| `covers` | **纯归属声明**：这片 glob 下的代码归本文档讲 | **否** | coverage（新代码必有主人）、warn（软提示可能受影响的文档）、size（covers 数走棘轮） |
| `contracts` | 「**改这个文件、不改文档，文档一定错**」的契约级集合（schema / 登记簿 / API 面 / token 定义） | **是** | strict（改契约文件却没同步文档就报红） |

为什么要拆：`covers` 为了 coverage 铺得很宽（常含整目录 `**`），若拿它触发 strict，改域里任何一个 helper、改个措辞都逼你动文档——假阳性。`contracts` 把「碰它文档必错」的那一小撮单独拎出来，strict 只认它，从「碰这个域就逼改文档」收窄成「碰真正的契约点才逼改文档」。

判据一句话：**「改这个文件而不改文档，文档一定错」才进 `contracts`**。典型进 `contracts` 的：`*Schemas.ts`、`syncDomains.ts` / `sync/domains.ts`（域登记簿）、`db/schema.ts`、`types.ts` 里被文档钉死字段的类型、API 路由契约、`index.css` token、控件目录 `ui/**`。纯实现文件、内部 helper 只进 `covers` 不进 `contracts`。

**`contracts` 与 `covers` 各自独立，不构成子集关系，绝不加子集校验。** `covers` 声明「这片代码归本文档讲」，`contracts` 声明「改这个文件本文档一定错」。多数文档的 `contracts` 确实取自它的 `covers`，但那是常见情形不是约束；加子集校验会把纵切与升格焊死。

每份 evergreen 的 `covers` / `contracts` 至少有一个非空，这是 no-gate：纵切且没有代码时用 `contracts`，纯代码入口地图用精确 `covers`。一份文档可以没有 `contracts`（如 development、stats-insights）——说明它没有「改某文件必错」的硬契约点，strict 对它天然是 no-op，这是诚实状态，不是漏配。共享契约文件（`syncDomains.ts`、`entitySchemas.ts` 等）可同时进多份文档的 `contracts`，等价于「改它 → 复查所有把它当契约的文档」，有意为之。

## 2. 主题文档骨架

新建主题文档默认使用这个稳定头（数据域用“数据流/Schema”，设计语言/模块主题可把 §1/§2 换成“规范/构成”等更贴切的小节名，但「承上启下」必留）。**逐节填之前先过 §0 内容边界**：每段都要能通过「没有改动发生时也成立」这一问。

```markdown
---
type: evergreen
title: <主题>
covers:
  - <本主题端到端代码路径>
contracts:
  - <schema / 登记簿 / API 面>
last-reviewed: YYYY-MM-DD
---

# <主题>
> 一句话定位 + 讲什么 / 不讲什么
<!-- 只写现状：机制 / 契约 / 不变量 / 边界。决策论证归 ADR，对 agent 的指令与授权归 AGENTS.md，
     改动流水归提交信息，在办事项归 docs_local。
     不写「目前 / 本轮 / 新增了 / 已改为」这类时间性措辞；一条 grep 或打开一个文件能得到的（prop 清单、
     className、函数签名）也不写。判据见 _docs-guide §0。此注释填完可删。 -->
```

`contracts:` 是可选块——「改它文档必错」的契约点集合（schema / 登记簿 / API 面），与 `covers` 无包含关系，触发 strict，见 §1.3。**`covers:` / `contracts:` 的冒号后必须什么都不写**，换行直接跟 `- item`：冒号后但凡有字符——**包括 `[]` 与行尾 `#` 注释**——`parseFrontmatter` 就把它当成标量值收下，底下那串 `- item` 一条都不再收集。`check:docs:size` 会把这种标量判成 `bad-type`；空列表写空块（`covers:` 后换行、不跟条目）或省略该块，别写 `covers: []`。所以上面两份模板的说明都写在代码块外，别贴回行尾。

## 3. 毕业阈值

通过 §0 后，内容的**安置有三个动作**：沿功能子域横切外提、沿读者路径纵切外提，或在长成独立主题时升格。前两者是外提的两条轴，先判该走哪条：**能沿功能子域切的走横切；功能子域已切尽、剩下的是跨子域公共层（流程 / 不变量 / 速查 / 排障）的，走纵切。** 升格的准入与动作见 §3.3。

**判轴前先消歧**：本节的轴相对**代码归属边界**而言——横切 = 沿功能子域把归属切开（`covers` 跟着走），纵切 = 垂直于它、按读者路径切开（`covers` 不动）。§1 那个「横切关注点/层」（architecture、data-model 这类跨所有主题的层）是另一个词，同名不同义：**跨全部子域的公共层在本节走的是纵切**。判反了会去迁一片与母主题全交叉的 `covers`，只能靠切碎或复制硬凑——而这种错切过得了全部门禁，没有闸会喊。

**下面两段两条轴共用**，只有准入判据分横 / 纵（§3.1 / §3.2）。

**外提动作**：把内容移到 `docs/evergreen/<主题>/<子主题>.md`（子目录，见 §1.1），**横切**要迁走对应 `covers:`、**纵切**不迁（母文档 `covers` 不变），在子文档顶部回链主题文档，在主题文档的“子文档索引”小节登记，重写链接与内部引用，再**全仓扫一遍入向引用**（下表第四类）。然后 `--write-size-baseline` 重写基线（新增子文档要落基线；横切还要更新母文档迁走后的 covers 数，纵切母文档 covers 数不变）。architecture 登记簿**不**新增子文档条目——它只认主题文档；升格另按 §3.3 办理。

**执行成本**：相对链接全要重写——被搬走的正文里 `[x](todo/x.md)` → `[x](x.md)`、`[x](x.md)` → `[x](../x.md)`、`[ADR](../adr/x.md)` → `../../adr/x.md`。`§x.y` 引用**分四类**（三类出向 + 一类入向），处置各不相同，逐条判完再动手：

| `§x.y` 的形态 | 它指谁 | 处置 |
|---|---|---|
| 紧跟在指向**别的文档**的链接后（`[tracks](tracks.md) §5`） | 那份文档的章节 | **章节号一个字不动**，只改链接路径 |
| **裸** `§x.y`（前面没有链接） | 母文档的章节 | 补前缀 → `[母文档](../<主题>.md) §x.y` |
| 指向**本次正被搬走**的那几节 | 已迁到新子文档 | 重指到子文档，**且编号形态会变**——原 `§3.4` 到了子文档里是第 4 个编号条目，写作 `[子文档](x.md) 第 4 条` |
| **入向**：别的文档、以及母文档剩下的正文，指向**本次被搬走**的那几节 | 已迁到新子文档 | 全仓 grep `](<主题>.md) §` 与裸 `§`，逐条重指到子文档的「第 N 条」或小节名 |

前三类都在手上这两份文件里，**第四类是唯一需要跨文档搜的**，也最容易整批漏掉：一次纵切在 6 份别的文档里留下 12 处入向引用，比任何一类出向引用都多。第一类是另一个主要陷阱：把「别的文档的章节号」误当母文档章节改掉，会静默指错而无人察觉——实测一次纵切里第一类 8 处、第二类 5 处，**陷阱比真目标还多**（这两个数是量级参考，不是核对清单，别数到数就收手）。`check:docs:links` 只对 Markdown 链接目标中的 `.md#id` 校验目标文档里独立成行的 `<a id="..."></a>` 显式锚点；不校验同页 fragment、Markdown 标题自动锚点或 prose 中的 `§x.y`，四类 prose 引用仍须人工逐条核。

**样例**：同步域是横切的样例——[sync](sync.md)（主题）索引 [sync/domain-registry](sync/domain-registry.md)（域登记簿）；纵切的样例见 §1.1 那两条例链。

### 3.1 横切：外提一个功能子域

只有子主题同时满足三条，才外提成独立子文档：

1. 它的 `covers:` 独立成簇，不与母主题其余部分交叉。
2. 体量过线：单文档 soft cap 约 15k 字符，hard cap 约 25k 字符；子主题段超过约 6k 字符时进入候选。
3. 它被独立编辑或引用，改它时通常不碰母主题其他段落。

这些数字是治理参考值，不是机械铁律。三条一起满足，才说明拆出去会降低维护成本。

母文档名下已有 **≥2 份横切子文档**时，横切轴多半已用尽，出路要往纵切找——`check:docs:size` 撞 hard cap 的报错会点名这类文档。纵切是否带 `covers` 取决于内容，不能仅凭 `covers` 非空把纯代码入口地图误判为横切。

**判完准入回 §3 前言动手**：搬迁步骤（外提动作）与 `§x.y` 四类处置表两条轴共用，只写在那里，本节不重复。

### 3.2 纵切：外提一条读者路径

横切三条件的第 1 条（`covers` 独立成簇）预设了拆分沿代码归属边界走。一个主题把功能子域切尽后，母文档剩下的是**跨全部子域的公共层**——它的 `covers` 与母主题全交叉，横切第 1 条永远不可能满足，于是母文档卡在 hard cap 上无路可走。纵切是这种情况下的合法出路。

同时满足四条才外提：

1. **独立消费**：只读这一份能得到完整价值，不必回母文档补上下文。
2. **访问路径不同**：读它的时机与母文档主体不同（改代码前读主体定位；出怪行为时查不变量；排障时查耗时观测）。操作化问法：**「这两节会不会在同一次任务里被一起读」**——会 → 同属一条路径，必须一起走；不会 → 是两条路径。这条同时干两件事：**圈定一条路径的完整边界**，以及**防滥用**（总被一起读的两节拆开只增加跳转成本，不拆）。
3. **体量过线**：判据 2 圈出的**整条路径**超过约 6k 字符。量的不是单个 `###` 小节——[todo](todo.md) 的「模块速查」下辖客户端 / 服务端 / 测试三节，单看客户端一节不过线，但三节是「找代码在哪」这一条路径、只能整体走。
4. **母文档移走后仍自足**：留一行索引，读者不点开也知道有这东西、何时该点。

触发词是「**混入**」，不是「太长」：Diátaxis 所说的 `explanation scattered in small parcels in other sections`，是解释被散落地混进其他章节，而不是章节字符一多就该拆。访问路径不同先于体量过线，先圈边界再量体量，避免按小节切碎。

**判据 2 先于判据 3**：顺序反了会把一条完整路径按小节切碎。判据 2 也天然限制数量：读者路径本就没几条，**每个主题纵切通常只产出 2–3 份**。

**陈述契约或不变量的纵切子文档 frontmatter**（纯 yaml，可整块复制）：

```yaml
---
type: evergreen
title: <主题> · <路径名>
covers:
contracts:
  - <schema / 登记簿>
last-reviewed: YYYY-MM-DD
---
```

上面这类文档的 `covers` 留空或省略都行，`contracts` 是它的机检闸。纯代码入口地图改为在 `covers` 列出正文实际指向的精确入口，`contracts` 留空或省略：改实现不会必然让「文件在哪」变假，但入口文件变化会经 `covers` 命中 warn。两类写法的冒号后都绝不能跟任何字符，`covers: []`、`contracts: []` 和行尾 `#` 注释都会被解析成标量并由 `check:docs:size` 拦下（机理见 §2）。`check:docs:size` 也会拦 `covers` 与 `contracts` 双空的 evergreen 文档。

**判完准入回 §3 前言动手**：搬迁步骤（外提动作）与 `§x.y` 四类处置表两条轴共用，只写在那里，本节不重复——入向那一类尤其别漏，它是唯一要全仓搜的。

### 3.3 升格：长成主题，就往上一层走

同时满足三条才升格为主题：

1. 经 §0.5 / §0.5b 筛过后仍超过 soft cap，不是靠删副本或缩措辞才显得大。
2. 它有独立的承上启下，能自己回答「是什么、怎么运作、边界在哪」，且它 `covers` 的那片代码与兄弟子文档不交叉。
3. 它自己仍需要再拆，能看出至少两个功能子域或读者路径；这是升格的实质理由，不是为了把文件挪到更高一层。

升格按六步办理：

1. 移到上一层，并按需建立自己的目录。
2. 在 architecture §6 文档登记簿登记为主题。
3. 把母文档的子文档索引改成承上启下的邻居链接。
4. 重写所有相对链接：`../x.md` → `x.md`、`../../adr/x.md` → `../adr/x.md`；子目录内互链 `x.md` → `<子>/x.md`。
5. 全仓扫描入向引用，按 §3 前言的四类分别处置。
6. 重写 size baseline，并核对输出的抬高清单。

母文档的 `covers` 不动，因为升格前那片 `covers` 本就在子文档身上，随文件走；升格改变的是导航层级与入口关系，不是借迁移悄悄扩大或收缩母主题的管辖。

## 4. 体量闸：字符走绝对上限，covers 走棘轮

`pnpm check:docs:size` 先守 frontmatter 形状，再守体量与管辖；**字符数不做棘轮**——正文想写多长写多长，只在单个文档真的膨胀到上限时才拦：

- **frontmatter 形状 = 硬闸**。evergreen 文档只接受 `type` / `title` / `last-reviewed` 三个必填标量，以及 `covers` / `contracts` 两个可选列表；未知键、缺必填键、列表被写成标量都会失败。ADR 不参与这条形状校验。
- **机检闸存在 = no-gate**。evergreen 文档不能 `covers` 与 `contracts` 双空：横切文档至少有 `covers`；纯代码入口地图列精确 `covers`；其他纵切文档若零 `covers` 就必须有 `contracts`。
- **字符数 = 绝对上限（cap），不是基线棘轮**。写作、补充、加例子随便加，不会因为「比上次长」而失败。只有单文档超过 **hard cap（约 25000 字符）** 才报错，含义是「这篇太长了，该拆」。**撞线时合法动作只有四条**：① 删过时 / 越界内容——越界内容不过时、只是放错层，按 §0.4 先补落点再 trim 成「一句现状 + 指针」，不许就地删；② **横切**外提一个功能子域；③ **纵切**外提一条读者路径；④ **升格**为主题（判据见 §3）。压缩措辞、删例子、把句子改短**不是**合法动作，四条都走不通就停下来问人。过 **soft cap（约 15000 字符）** 只软提示、不失败。软提示按余量分三档（超 15000 起 🟡 / 超 20000 起 🟠 / 超 23000 起 🔴，边界是严格大于），措辞随逼近程度加重——同一句警告长期不变会退化成背景噪音，分档是为了让「快撞线了」这件事仍然可感。
- **`covers` 数 = 棘轮（只增要过基线）**。`scripts/evergreen-size-baseline.json` 只记每篇文档的 `covers` 数与存在性；某文档 `covers` 数比基线大会报错——防止一篇文档悄悄把越来越多代码划进自己管辖。基线**不再记字符数**。
- 基线必须覆盖当前全部 evergreen 文档；新增 / 删除 / 重命名 evergreen 文档后不更新基线会失败（缺项 / 含已删文档都报）。
- ADR 不参与体量闸；ADR 是决策记录，只追加。

合理扩大 `covers` 管辖时（真实职责扩展），跑 `--write-size-baseline` 重写基线并在提交信息说明原因。字符增长不需要重写基线。

**这个写基线是整体重写**（基线是 filePath → covers 的完整映射，新增 / 拆分 / 删除文档都要求条目全量重建，做不成单条增量），所以它同时会把**工作树里当时全部**的 covers 增长一并收编。为免棘轮被静默放松，写完会逐条打印被抬高的 `covers`（`old → new`）与新增 / 移除 / 收窄的文档：**跑完必须看那份 ⚠️ 清单**，只留本次改动应得的那几条，其余说明你重写早了（先提交或还原别的改动再重写）。同源问题在 `scripts/check-test-hygiene.mjs` 走的是另一条路——那份基线是扁平 key 列表，可以单条增量，故已把 `--write-baseline` 换成 `--add <路径>` / `--prune` / `--rewrite-baseline`（见 [development](development.md)）。

## 5. 检查脚本闭环

`scripts/check-evergreen-docs.mjs` 的几个 mode 合起来让文档体系自洽（全在 CI 跑）：

| 命令 | 守什么 | 失败条件 |
|---|---|---|
| `check:docs:strict --since=<base>` | **改了契约点 → 同步对应文档** | 改动命中某文档 `contracts`（非 `covers`）但该文档没一起改；见 §1.3 |
| `check:docs:coverage --since=<base>` | **加了源码 → 必须有文档认领** | 新增 `packages/*/src/**` 文件不匹配任何 covers，且非豁免（测试/`.d.ts`/mock/夹具/story） |
| `check:docs:size` | **frontmatter 有效、单文档别膨胀到该拆** | frontmatter 形状错误、`covers`/`contracts` 双空、字符数超 hard cap（≈25k，按 §4 的四条合法动作处置：删过时 / 越界内容、横切、纵切、升格；字符不做棘轮），或 `covers` 数超基线，或基线漏项/含已删文档 |
| `check:docs:links` | **互链/指针别指向消失的文档** | evergreen 内、以及 `AGENTS.md` / `README.md` 指向 evergreen·ADR 的 `[..](x.md)` 指向不存在的 .md |
| `check:docs:stale` | **last-reviewed 别过期** | 超 180 天或缺字段 |

脚本在「要动 evergreen 文档」的时刻打印 §0 内核摘要（判据一句话 + 四个归属去向 + 指针回本文）：strict / coverage 失败时印在报错后；改动集里含 evergreen 正文（不含 ADR）时无论过不过都印一行自查提醒。摘要文本住在脚本的 `EVERGREEN_RULES_SUMMARY`，只抄 §0 最稳定的内核——§0 内核变了要同步它。

闭环含义：**新代码必有主人（coverage）→ 改契约点名文档（strict，认 `contracts`）→ 文档不膨胀（size）→ 三层互链不断（links）**。新增源码若暂不值得专门文档，要么归进最贴近主题的 covers，要么确属测试/类型/夹具时加进脚本的 `COVERAGE_EXEMPTS`。
